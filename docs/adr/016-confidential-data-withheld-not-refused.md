# ADR 016: Confidential data is withheld from unauthorized endpoints, the work goes ahead

- **Status:** accepted; supersedes the enforcement and start-up parts (3 and 4) of ADR 015. The rule itself (confidential text reaches only authorized endpoints) is unchanged.
- **Date:** 2026-10-28

## Context

ADR 015 refused any vault-tagged call without a sanctioned endpoint (HTTP 503) and made production refuse to start with an empty allowlist. The owner's intent is different: Scout must keep working. Runs, matching, joint ideas and document ingestion go ahead, and the user's confidential data is simply not sent to a provider nobody authorized for it.

## Decision

1. **Two data classes.** *Published* data (OpenAlex works, profile fields the user made public) may go to any endpoint. *Confidential* data (vault documents, unpublished text, and anything derived from them: passages, insights, keywords, the profile statements and the other person's statements built from them) may go only to authorized endpoints. Unclassified means confidential.
2. **Classification per input item.** Every agent input model derives from `AgentInput` (`scout.shared.confidential`) and must declare each field with `published_field`, `confidential_field` or `mixed_items_field` (list items classify themselves through `is_confidential`). A field without a declaration is a `TypeError` when the class is defined, so confidential text cannot be added to a published-class prompt by omission. `AgentSpec.data_class` (prompt front-matter) is `published` or `confidential` (default); the per-field tags decide what actually carries confidential content.
3. **One policy.** `input_for_route(agent_class, input, authorized=...)` is pure: an authorized route gets the input unchanged (sent as confidential only if a confidential part is non-empty); an unauthorized route gets the input with every confidential part withheld, sent as published; an input that cannot be classified or emptied (not an `AgentInput`, a confidential field without default, a wholly confidential agent such as `InsightExtractor` or `InsightTopicTagger`) is not sent at all. `AgentFactory.run` applies it to every call, so no agent builder has to remember.
4. **Who reports `authorized`.** The adapter, through `LLMPort.confidential_allowed(tier)`. `LlmRouterAdapter` is true only when the route of that tier has authorized deployments; a confidential request is pinned to a derived route `<route>__confidential` that holds authorized deployments only, so fall-over can never reach an unauthorized one. `MeteringCompletion` still re-checks the model before every provider request. In doubt (a tier without an authorized deployment, an unknown route) the answer is no. If every authorized deployment fails, the call fails and the job retries; it never falls back to an unauthorized endpoint with the confidential input.
5. **Use cases decide up front.** Discovery asks `agents.confidential_allowed()`: when false, `StepContext.material()` returns no vault material, the run is stored with `basis = published_only` (in `RunInputs`, no migration), opportunities carry it in `score_basis`, and `RunOut` / `OpportunityCardOut` return `basis` and a fixed `basis_note`. The evidence rule is untouched (at least two verified items; vault evidence cannot be cited because it was never offered). Matching leaves consented vault statements out of the profile job and the joint-ideas input. Vault ingestion parses locally, then, when no authorized endpoint exists, parks the document in the new status `awaiting_approved_provider` (kept, chunks stored, not failed); the vault sweep requeues parked documents when an endpoint becomes available. Under `discard` retention the stored text stays until the document is analysed (or deleted).
6. **Start-up.** No refusal for an empty allowlist. One warning is logged at start (`confidential_data_disabled`) and `GET /system/status` returns `confidential_data_enabled` and `confidential_data_notice` (no secrets). `LLM_FREE_PROVIDERS_ACKNOWLEDGED` is removed: with no authorized provider free tiers see published data only, and a provider the owner authorizes has had its terms confirmed by that act.
7. **Names.** `sanctioned` becomes `authorized` (`sanctioned` is still read in `llm_router.yaml`), `LLM_VAULT_SANCTIONED_PROVIDERS` becomes `LLM_CONFIDENTIAL_AUTHORIZED_PROVIDERS`, `LLM_VAULT_ALLOW_ANY_PROVIDER` becomes `LLM_CONFIDENTIAL_ALLOW_ANY_PROVIDER` (the old environment names are accepted as aliases). `VaultDataRefused` becomes `ConfidentialDataRefused` and survives only as a backstop that users should never see. "Vault" stays the name of the product area.

## Consequences

- Out of the box nothing confidential leaves the process, and the product still works on published data. The owner enables confidential use later by marking deployments `authorized: true` and listing the provider (BLOCKERS B6).
- Results without documents are less specific. The UI says so on the run, on each opportunity, on the vault page and on the document row.
- Vocabulary-level labels (controlled-vocabulary method names, topic ids, numeric weights) are treated as published even when a vault insight raised their weight; they carry no document text (as in DECISIONS 109).
- A stored profile or run computed while authorized is not rewritten when authorization is removed; the next recomputation uses published data only.
- Not done here: a vault-free retry of a request when all authorized deployments are down (the job retries instead); recomputing existing runs after authorization (F-54).
